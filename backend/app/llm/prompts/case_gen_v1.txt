## Coverage requirements

Distribute the target cases roughly across these buckets (skip a bucket if
this chapter does not justify it; document why in `coverage_notes`):

- **happy** — primary success paths
- **edge** — boundary values, empty/very-long inputs, special characters
- **error** — invalid inputs, bad credentials, missing required fields
- **security** — only if PRD mentions auth / permissions / sensitive data

## Explicit post-action milestones

If the PRD chapter explicitly says a user-visible milestone must happen after
an action, include that milestone in both `steps[].expected` and
`assertions[]`. Do not stop at the submit/click action.

Examples:
- If PRD says **Email Verification** or "email verification required after
  initial registration", the registration happy-path case must submit valid
  registration data and then expect a verification/check-email state, not a
  completed account.
- If PRD says "after first login following verification", keep that as a
  separate post-verification flow/precondition; do not merge it into the
  initial registration case unless the UI can actually complete verification.

## PRD traceability requirements

Every generated case must be grounded in the PRD chapter text, not just the
chapter title or generic product assumptions.

- For every assertion, include an `evidence` field with a short exact quote or
  very close excerpt from the PRD chapter that supports that assertion.
- Use `source: "prd_explicit"` ONLY when the assertion is directly supported by
  that `evidence` quote.
- If the PRD does not explicitly state the expected behavior, do not invent it.
  Either return fewer/zero cases, or mark the assertion as `domain_inferred` or
  `exploratory` with confidence <= 0.6 and explain the gap in `rationale`.
- Do not create cases from the chapter title alone. If the body has too little
  browser-testable detail, return an empty `cases` array and say so in
  `coverage_notes`.

## Auth-state classification (decide PER CASE before writing steps)

Each case implicitly belongs to ONE of these auth states. Pick the right
one — getting this wrong makes the case fail or test the wrong thing.

### A) `logged-in` — feature lives behind a login wall (most common)

E.g. 修改密码 / 查看订单 / 发帖 / 个人资料编辑.

**If Login context above provides project credentials**, prepend these
steps to the case (do NOT put login in `preconditions` only — the agent
needs actionable steps):

1. 打开登录页 (e.g. `/login` / `/logins` / `/signin` under base_url)
2. 在邮箱/用户名输入框输入 `<project default_username>`
3. 在密码输入框输入 `<project default_password>`
4. 点击登录按钮 | 期望: 跳转到非登录页（如 /home, /dashboard）
5. ... 然后才是该 case 真正的测试步骤

If credentials are NOT configured, leave login out of steps and write
`preconditions: ["user is logged in (manual setup needed)"]`.

### B) `logged-out` — feature MUST be tested without an existing session

E.g. **注册 / 忘记密码 / 登录 UI 本身的渲染**.

- 不要 prepend 登录步骤
- `preconditions: ["fresh browser session, user is NOT logged in"]`
- 第一步通常是 `navigate to base_url` 或直接 `/register` / `/login`
- 这种 case 即使项目有默认账号，agent 在运行时也不应该用它登录

### C) `deliberately-wrong-creds` — testing rejection / error message

E.g. 测试 "密码错误时显示提示" / "邮箱不存在时跳转".

- 不要用项目默认账号
- 在 step 里**显式**写错误的凭证作为参数:
  `输入 "wrong-password-xxx" 到密码框`
- 断言聚焦在错误提示是否出现、URL 是否未跳转

### D) `public` — auth-irrelevant (marketing/docs/search/health pages)

跳过整个登录话题，直接写步骤。

## Hard rules

- Output ONLY the JSON object above. No markdown fences, no commentary.
- Every step.intent must be **executable by a browser agent**: refer to
  visible UI elements ("点击 '保存' 按钮"), not to internal API or DB state.
- Prefer 4-10 steps per case. Pad obvious wait/verify steps if needed.
- If multiple chapters are provided, set `chapter_id` to the exact chapter id
  shown in that chapter heading.
- Assertion descriptions must be falsifiable. Avoid vague words like "正常".
- For every assertion, set `source`:
  - `prd_explicit`: the PRD chapter clearly states this expected behavior.
  - `domain_inferred`: reasonable product/QA inference, but not explicit.
  - `exploratory`: boundary/security/data exploration that needs human confirmation.
- For every assertion, set `evidence`:
  - Required and non-empty for `prd_explicit`.
  - Must quote or closely excerpt the PRD chapter text, not the chapter title.
  - Leave empty or explain the missing PRD basis for `domain_inferred` /
    `exploratory`.
- Do NOT invent exact error copy. If PRD does not specify text, assert the
  safer outcome instead: invalid data is rejected, no invalid transaction/result
  is created, or the corrected legal value is clear to the user.
- Boundary-value tests should not directly claim product bugs unless the PRD
  states the expected behavior. Mark them `exploratory` or `domain_inferred`.
- **Set `auth_state` on every case** to exactly one of `logged-in` /
  `logged-out` / `wrong-creds` / `public` (the four classes above).
  This is a top-level field, NOT a string inside `tags`. The runtime
  executor reads it to decide whether to auto-login.
- If the PRD chapter is empty/garbage, return an empty `cases` array and
  `coverage_notes` explaining why.
